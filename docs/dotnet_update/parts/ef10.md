## Entity Framework Core 10

### EF ツールで、マルチターゲット プロジェクトにフレームワークを指定する必要があるようになった
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **`dotnet ef`（EFツール）とは**
  `dotnet ef migrations add`（マイグレーション＝DBスキーマの変更差分を作る）や`dotnet ef database update`（そのマイグレーションを実際のDBに適用する）といったコマンドを実行するための、dotnet CLIの拡張ツール。EF Coreを使うプロジェクトでは開発中に頻繁に叩くコマンド。
- **マルチターゲット（`TargetFrameworks`、複数形）とは**
  1つの`.csproj`から、同時に複数の.NETバージョン向けにビルドできるようにする設定。たとえばNuGetパッケージを作る側が「.NET 8でも.NET 10でも使えるようにしたい」というときに使う。`<TargetFramework>net10.0</TargetFramework>`（単数形、1つだけ）が普通のアプリの書き方で、`<TargetFrameworks>net8.0;net10.0</TargetFrameworks>`（複数形、セミコロン区切り）がマルチターゲットの書き方。
- **MSBuildタスクとは**
  `dotnet build`の裏側で実際にコンパイルやファイルコピーなどの作業を行う処理単位。`ResolvePackageAssets`は「このプロジェクトが参照しているNuGetパッケージの中身（DLLの場所など）を解決する」タスクで、対象フレームワークが1つに定まっていないと正しく動かせない。

【説明】

以前は、複数フレームワーク対象（マルチターゲット）のプロジェクトでも、`dotnet ef migrations add`のようなコマンドをフレームワーク指定なしでそのまま実行できた。

EF Core 10.0以降、EFツールの内部実装が`ResolvePackageAssets`というMSBuildタスクに依存するようになったが、このタスクはマルチターゲットプロジェクトでは（対象フレームワークが1つに定まらないため）使えない。そのため、`<TargetFrameworks>`（複数形）を使っているプロジェクトに対して`--framework`オプションなしでEFコマンドを実行すると、「プロジェクトは複数のフレームワークを対象としています」というエラーで失敗するようになった。

【放置したときの影響】

このプロジェクトのようにマルチターゲットを使っていない場合は無関係。もし実務の別プロジェクトでマルチターゲットのクラスライブラリにEF Coreを載せている場合、.NET 10へのEF Coreアップグレード後に、これまで動いていた`dotnet ef migrations add`コマンドが突然エラーで止まるようになる（ビルド自体は成功するが、EFツールの実行だけ失敗する）。

【プロジェクトでの調べ方】

1. EF Coreを実際に使っているか確認する。`Microsoft.EntityFrameworkCore`でリポジトリ全体をgrepしたところ、`shared/DicomTool.Shared`（DbContextと各Entityの定義）、`backend/DicomTool.Api`（GraphQL経由の読み書き）、`services/DicomTool.Worker`（Temporal Activity経由の書き込み）で使用していることを確認した。DBプロバイダーは`shared/DicomTool.Shared/DicomTool.Shared.csproj`に`Npgsql.EntityFrameworkCore.PostgreSQL`（PostgreSQL用）が参照されており、`docker-compose.yml`のPostgreSQLコンテナに対応している（`DicomDbContextFactory.cs`のコメントにも「dicom-tool(旧)のSqliteから乗り換える」と明記されている）。
2. マイグレーションを実際に持っているプロジェクトである`shared/DicomTool.Shared/DicomTool.Shared.csproj`を確認したところ、`<TargetFramework>net10.0</TargetFramework>`と**単数形**で書かれており、マルチターゲットではなかった。念のため他の全`.csproj`（`backend/DicomTool.Api`、`backend/DicomTool.Api.Tests`、`services/DicomTool.Worker`、`services/DicomTool.DicomScp`、`services/DicomTool.StorageGuard`、`services/DicomTool.TrayApp`、`frontend/timeline/DicomTool.Timeline`）もgrepしたが、すべて`TargetFramework`単数形で、`TargetFrameworks`（複数形）を使っているプロジェクトは1つもなかった。
3. → **このプロジェクトは現時点でこの破壊的変更の影響を受けない。** `dotnet ef migrations add`を今まで通り`--framework`なしで実行して問題ない。

【改修方法】

現状は対応不要。将来もし`DicomTool.Shared`をマルチターゲット化することがあれば、EFコマンドの実行時に対象フレームワークを明示する。

```bash
dotnet ef migrations add MyMigration --framework net10.0
```

### アプリケーション名が接続文字列に挿入されるようになりました
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **接続文字列（Connection String）とは**
  「どのDBサーバーに、どのユーザー名・パスワードで、どのDB名に接続するか」をまとめて1行のテキストで表したもの。例:`Host=localhost;Port=5432;Database=dicomtool;Username=dicomtool;Password=...`のような形式。
- **`Application Name`パラメーターとは**
  接続文字列の中に含められる項目の1つで、「このDB接続は、どのアプリケーションから来たものか」をDBサーバー側に伝える名札のようなもの。DBサーバーの管理画面やログで「今どのアプリからどんな接続が来ているか」を見分けるのに使われる。
- **コネクションプール（接続プール）とは**
  DBへの接続（コネクション）を毎回新規に張り直すのはコストが高いため、一度作った接続を使い回す仕組み。多くのDBクライアントライブラリ（ADO.NET系）は、**接続文字列の内容が完全に一致する接続同士だけ**を同じプールとして使い回す。接続文字列が少しでも違えば「別のプール」として扱われる。
- **`TransactionScope`と分散トランザクションとは**
  複数のDB接続にまたがる処理を「全部成功するか、全部失敗するか」の単位でまとめたいときに使う仕組み。同じDBに対する接続でも、コネクションプールが分かれている（＝別の物理接続とみなされる）と、DB的には「複数の接続」として扱われてしまい、通常より重い「分散トランザクション」に自動的に格上げ（エスカレーション）されることがある。分散トランザクションは設定や環境によっては動かない・遅いといった問題を起こしうる。

【説明】

EF Core 10.0以降、接続文字列に`Application Name`が指定されていない場合、EFとADO.NETドライバー（SQL Serverプロバイダーの場合はSqlClient）のバージョン情報を含む`Application Name`が自動的に挿入されるようになった。

これ自体は診断のしやすさ向上が目的だが、副作用として、**同じDBに対してEF Core経由の接続と、Dapperや素のADO.NETなど別の技術経由の接続を両方使っている**場合、それぞれの接続文字列の`Application Name`部分が異なることになり、ドライバーは「別の接続文字列＝別のプール」と判断してコネクションプールを分けてしまう。この状態で`TransactionScope`を使って両方の接続にまたがる処理を書いていると、意図せず分散トランザクションへのエスカレーションが発生する可能性がある。

【放置したときの影響】

公式の影響度は「低」。このプロジェクトのように、EF Core経由のアクセスしかなく、Dapper等の別技術で同じDBに接続していない構成であれば、実害は基本的にない。もし将来Dapperなどを併用し始めた場合に、原因不明の分散トランザクションエラーとして顕在化しうる。

【プロジェクトでの調べ方】

1. `backend/DicomTool.Api/appsettings.json`の`ConnectionStrings:Dicom`（`Host=localhost;Port=5432;Database=dicomtool;Username=dicomtool;Password=dicomtool_dev_password`）を確認したところ、`Application Name`は明示的に指定されていなかった。
2. リポジトリ全体を`Dapper`でgrepしたが1件もヒットせず、EF Core以外の手段で同じPostgreSQLに接続しているコードは見当たらなかった。よって`TransactionScope`混在によるエスカレーションのリスクは現時点ではない。
3. なお、この変更は元々SQL Serverプロバイダー（`Microsoft.Data.SqlClient`）を念頭に置いた説明になっている。このプロジェクトが使っているのはPostgreSQL用の`Npgsql.EntityFrameworkCore.PostgreSQL`であり、挙動の詳細（バージョン情報の埋め込み方など）が完全に同じとは限らない点に注意（Npgsqlも独自に`Application Name`を扱うが、実装はNpgsql側の変更履歴に依存する）。

【改修方法】

現状は対応不要。将来Dapper等を併用する設計に変える場合は、`appsettings.json`の接続文字列にあらかじめ`Application Name=DicomTool.Api`のように明示しておくと、EFに上書きされず、他の技術と同じ接続文字列（＝同じプール）を維持しやすくなる。

### Azure SQL と互換性レベル 170 で既定で使用される SQL Server json データ型
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **SQL Serverの「互換性レベル」とは**
  SQL Server（やAzure SQL）が持つ、「このDBはSQL Serverのどのバージョン相当の挙動をするか」を切り替える設定値（例: 160=SQL Server 2022相当、170=次期バージョン相当）。新しい互換性レベルほど新機能が使えるが、挙動が変わることもある。
- **`json`データ型とは**
  SQL Serverの新しいネイティブなJSON専用データ型。それ以前は、JSON文字列は普通の文字列型（`nvarchar(max)`、可変長の文字列を格納できる列）にそのままテキストとして保存するしかなかった。
- **所有型（Owned Type）・プリミティブコレクションのJSONマッピングとは**
  EF Coreで「1つのエンティティの中に埋め込まれた複合的なデータ（住所オブジェクトや、タグの配列など）」を、別テーブルに分けず1つの列にJSON文字列として丸ごと保存する機能。

【説明】

以前は、所有型やプリミティブコレクション（文字列のリストなど）をJSONとして1列にマッピングする場合、SQL Serverプロバイダーは`nvarchar(max)`（テキスト）列に格納していた。

EF Core 10で`UseAzureSql`を使うか、SQL Server自体で互換性レベル170以上を使っている場合、これらは新しい`json`データ型にマッピングされるようになった。新しい型はパフォーマンスが良い反面、SQL Server側の`json`型はまだ機能が制限されており（例: `json`型の配列に対する`DISTINCT`が使えない）、一部のLINQクエリが実行時エラーになる可能性がある。また既存のテーブルがある状態でこの変更を含むEF 10へアップグレードすると、既存の`nvarchar(max)`列を`json`型に変換するマイグレーションが自動生成される点にも注意が必要。

【放置したときの影響】

このプロジェクトでは無関係。

【プロジェクトでの調べ方】

`shared/DicomTool.Shared/DicomTool.Shared.csproj`のパッケージ参照を確認したところ、DBプロバイダーは`Npgsql.EntityFrameworkCore.PostgreSQL`（PostgreSQL用）のみで、`Microsoft.EntityFrameworkCore.SqlServer`や`UseSqlServer`/`UseAzureSql`の呼び出しはリポジトリ全体をgrepしても1件もヒットしなかった。この変更はSQL Server／Azure SQLプロバイダー固有の話であり、PostgreSQLを使う本プロジェクトのDBスキーマには影響しない。

【改修方法】

対応不要。

### パラメーター化されたコレクションで既定で複数のパラメーターが使用されるようになりました
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **`.Where(x => ids.Contains(x.Id))`のようなクエリとは**
  「変数`ids`（C#側のリストや配列）に含まれるIDのどれかに一致する行を取得する」という、実務で非常によく書くLINQクエリ。EF CoreはこれをSQLの`WHERE Id IN (...)`に変換してくれる。
- **クエリプランとは**
  DB側が「このSQLをどういう手順（インデックスを使うか、全件走査するかなど）で実行するか」をあらかじめ決めた実行計画。同じ形のSQLでも中身のデータ量によって最適なプランが変わることがある。
- **カーディナリティとは**
  「このIN句の中に何個の値が入っているか」といった、件数に関する情報。DBの最適化エンジンはこれを知っているほど賢いプランを立てやすい。

【説明】

以前は、`.Where(x => ids.Contains(x.Id))`のようなクエリは既定で1つのJSON配列パラメータ（SQL Serverでは`OPENJSON`関数で展開）に変換されていた。ids の中身が何件あっても、SQLパラメータは1個で済む代わりに、DB側は「配列の中身が何件あるか」を実行するまで正確に把握しづらかった。

EF Core 10.0以降は既定で、`WHERE Id IN (@ids1, @ids2, @ids3)`のように、リストの要素1つにつき1つのSQLパラメータを生成するスカラーパラメータ方式に変わった。これによりDBの最適化エンジンに件数（カーディナリティ）の情報が伝わり、多くの場合クエリプランが改善する。ただし、リストの件数が非常に多い場合や特定のクエリパターンでは、逆にパフォーマンスが悪化する可能性もある。

【放置したときの影響】

公式の影響度は「低」。動作自体は変わらず結果も同じだが、生成されるSQL文の形とパラメータ数が変わるため、パフォーマンス特性が変わりうる。特にコレクションの要素数が可変・大量になりうる検索機能があると、体感速度が変わる可能性がある。

【プロジェクトでの調べ方】

1. `backend/`配下のC#コードを`.Contains(`でgrepしたところ、テストコードの`Assert.Contains(...)`（アサーション用でLINQのContainsではない）が1件ヒットしたのみで、DBクエリとして`リスト変数.Contains(x.プロパティ)`のようなパターンは現時点で見当たらなかった。
2. `shared/DicomTool.Shared/GraphQL`（`Query.cs`/`Mutation.cs`）も確認したが、現状のクエリはID単体指定や`Order`によるページングが中心で、複数IDのIN句検索機能はまだ実装されていない。
3. → 現時点ではこの変更が実際に効いてくる箇所は無いが、将来「複数のStudy/SeriesをまとめてIDで取得する」ようなAPI（例:一括既読化、一括削除でのID配列受け取り）を実装した際には、この挙動変化を意識する必要がある。

【改修方法】

現状は対応不要。将来複数ID検索を実装し、パフォーマンス上の懸念（IDが数千件単位になる、等）が出てきた場合は、クエリ単位で明示的に制御できる。

```csharp
// 従来通りJSON配列1パラメータにしたい場合
var studies = await context.UserStudies
    .Where(s => EF.Constant(ids).Contains(s.Id))
    .ToListAsync();

// グローバルに既定の挙動を変える場合（Program.cs等でのUseNpgsql設定時）
optionsBuilder.UseNpgsql(cs, o => o.UseParameterizedCollectionMode(ParameterTranslationMode.Constant));
```

### ExecuteUpdateAsync が通常のラムダを受け入れるようになりました
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **`ExecuteUpdateAsync`とは**
  該当する行をいったんC#のオブジェクトとして読み込んでから1件ずつ更新する（`SaveChangesAsync`の一般的な流れ）のではなく、`UPDATE`文を直接発行して一括更新するAPI。「未読を全部既読にする」のような一括更新処理で使う。
- **式ツリー（`Expression<Func<...>>`）とは**
  C#のラムダ式（`x => x.Foo`のような書き方）を、実行可能なコードとしてではなく「構文木データ」として保持する仕組み。EF CoreはこれをSQLに変換するために使う。ラムダ式を人間が普通に書く分には意識しなくてよいが、コードで動的に組み立てようとすると（`Expression.Lambda`などのAPIを直接使う必要があり）とても複雑になる。
- **通常のデリゲート（`Func<...>`）とは**
  式ツリーと違い、普通のC#コード（`if`文やメソッド呼び出しを含む）としてそのまま実行できるラムダ式・メソッドの型。

【説明】

以前は`ExecuteUpdate`の更新内容を指定する引数は式ツリー必須で、「条件によって更新する列を変える」といった動的な処理を書こうとすると、`Expression.Lambda`などを手作業で組み立てる必要があり複雑だった。

EF Core 10.0以降、通常のデリゲート（`Func<...>`）でも受け付けるようになり、`if`文で条件分岐しながら`SetProperty`を呼ぶ、という直感的な書き方ができるようになった。

【放置したときの影響】

これは「できることが増える」変更であり、破壊的変更というより機能追加に近い。既存の`ExecuteUpdate`呼び出し（式ツリー形式）はそのまま動き続けるため、何もしなくても壊れることはない。

【プロジェクトでの調べ方】

リポジトリ全体を`ExecuteUpdate`／`ExecuteDelete`でgrepしたが1件もヒットせず、このプロジェクトでは現状`ExecuteUpdateAsync`/`ExecuteDeleteAsync`を使った一括更新・一括削除は実装されていない（`services/DicomTool.Worker/Activities/DeleteRecordActivity.cs`や`RegisterDicomRecordActivity.cs`を見ても、通常のEntity取得→プロパティ変更→`SaveChangesAsync`という流れになっている）。

【改修方法】

現状は対応不要。ただし今後「未読を一括既読化する」「複数レコードのステータスをまとめて更新する」といった機能を実装する際は、`ExecuteUpdateAsync`の採用を検討する価値がある（読み込み→変更→保存より高速）。その際、通常のラムダ+`if`文で条件付き更新を書けることを知っておくと実装が楽になる。

```csharp
// EF Core 10以降なら、こう書ける
await context.UserSops
    .Where(sop => sop.UserSeriesId == seriesId)
    .ExecuteUpdateAsync(setters =>
    {
        setters.SetProperty(sop => sop.IsRead, true);
        if (markOrderToo)
        {
            setters.SetProperty(sop => sop.Order, newOrder);
        }
    });
```

### 複合型の列名が一意化されるようになりました
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **複合型（Complex Type）とは**
  EF Coreの機能の1つで、「独立したエンティティ（主キーを持つテーブル）にはしたくないが、複数のプロパティをひとまとまりのオブジェクトとして扱いたい」場合に使う型（例:「住所」を`Street`/`City`/`Zip`の3プロパティを持つ`Address`型としてまとめ、親エンティティのテーブルにそのまま列として展開する）。所有型（Owned Type）に似ているが、より軽量な位置づけ。このプロジェクトではまだ使われていない機能。

【説明】

以前は、複合型を通常のテーブル列にマッピングする際、異なる複合型に含まれる同名のプロパティ（例えば`HomeAddress.City`と`WorkAddress.City`）が、構成の仕方によっては暗黙的に同じ列名（`City`）を共有してしまい、意図せずデータが上書きされる事故が起きうる状態だった。

EF Core 10.0以降は、同名列が衝突する場合、自動的に末尾へ連番を付けて一意な列名にするようになった（例:`City1`、`City2`）。

【放置したときの影響】

このプロジェクトでは無関係（複合型を未使用のため）。将来複合型を使い始めた場合、これまで意図せず同名列で衝突していた構成があると、マイグレーション実行時に列名・列数が変わる形で顕在化する。

【プロジェクトでの調べ方】

`shared/DicomTool.Shared/Data/DicomDbContext.cs`の`OnModelCreating`と、`Entities/`配下の各エンティティ（`UserStudy`/`UserSeries`/`UserSop`/`AppUser`）を確認したが、`ComplexProperty`や複合型の定義は存在しない。またリポジトリ全体を`ComplexProperty`でgrepしても該当なし。現状は通常のスカラープロパティのみで構成されたシンプルなエンティティ設計になっている。

【改修方法】

対応不要。

### 入れ子になった複合型のプロパティでは、列名に完全なパスが使用されます
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **入れ子になった複合型とは**

### SQL パラメーター名が簡略化されました
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **SQLパラメーター名とは**
  EF Coreが生成するSQL文の中で、値を埋め込む代わりに使うプレースホルダーの名前（例:`WHERE "PatientId" = @city`の`@city`部分）。値そのものではなく名前なので、ログや実行計画に表示される。
- **クエリプランのキャッシュとは**
  DBサーバーは、一度実行したSQL文（の形）に対して「こう実行するのが最適」というプランを記憶しておき、同じ形のSQL文が来たら使い回すことで高速化している。SQL文のテキスト（パラメータ名を含む）が変わると、DB側は「別のSQL文」とみなし、キャッシュ済みのプランを再利用できず、初回だけ余分にプラン作成のコストがかかる。

【説明】

以前は、EF Coreが生成するSQLパラメータ名は`@__city_0`のような、アンダースコア始まりの接頭辞＋連番という機械的な名前だった。

EF Core 10.0以降は、元になったC#の変数名やメンバー名に近い`@city`のような読みやすい名前になり、同じ名前が複数登場する場合のみ数字のサフィックスが付く（例:`@city`、`@city1`）。これは生成されたSQLをログやクエリプラン、診断ツールで見たときに分かりやすくするための変更。

【放置したときの影響】

公式の影響度は「低」で、通常はEF Coreの内部で完結する透過的な変更のため、アプリのコードを直す必要は基本的にない。ただし例外的に、①生成SQLの正確な文字列（パラメータ名込み）をアサートしているスナップショットテストがある場合、②SQLログやクエリプランを見るインターセプター・監視ツールでパラメータ名のパターンに依存した処理をしている場合は影響を受ける。また、アップグレード直後はDBサーバー側に溜まっていた「旧パラメータ名前提のキャッシュ済みクエリプラン」が使えなくなり再コンパイルが発生するため、切り替え直後の一時的な負荷増加に注意が必要（本番導入時に知っておくとよい注意点）。

【プロジェクトでの調べ方】

1. `backend/DicomTool.Api.Tests`配下のテストコードを確認したが、生成SQL文字列やパラメータ名を直接アサートしているテスト（`ToQueryString()`の結果を検証するようなテストなど）は見当たらなかった。GraphQLのレスポンス内容を検証するテスト（`LoginMutationTests.cs`等）が中心で、SQLの内容そのものには依存していない。

3. → **現状のテスト・実装はこの変更の影響を受けない。**

対応不要。ただし本番のPostgreSQL環境へこのバージョンをデプロイする際は、切り替え直後にDB側でクエリプランの再コンパイルが集中し、一時的にレイテンシが上がる可能性がある点を運用上のリスクとして頭に入れておくとよい（性能問題ではなく、初回だけの一過性のもの）。

#### Microsoft.Data.Sqlite の破壊的変更

以下の3項目は、`Microsoft.Data.Sqlite`（SQLite用のADO.NETドライバー）バージョン10で、日時（`DateTime`/`DateTimeOffset`）とタイムゾーンの扱いが「実行しているPCのローカルタイムゾーン依存」から「UTC（協定世界時）基準」に変更されたことによるもの。3つとも根っこの原因は同じで、SQLite自体の一般的な慣習（日時はUTCで保存するのが定石）にドライバーの挙動を合わせるための変更。

いずれの項目も、どうしても旧動作（ローカルタイムゾーン依存）に戻したい場合は、次のAppContextスイッチを`true`に設定することで一時的に回避できる（あくまで最終手段・移行期間中の一時しのぎとしての位置づけで、恒久的な解決策ではない）。

```csharp
AppContext.SetSwitch("Microsoft.Data.Sqlite.Pre10TimeZoneHandling", isEnabled: true);
```

### オフセットなしで GetDateTimeOffset を使用すると、UTC が想定されるようになりました

### オフセットで GetDateTime を使用すると、UTC で値が返されるようになりました
リンク：https://learn.microsoft.com/ja-jp/ef/core/what-is-new/ef-core-10.0/breaking-changes

【前提知識】

- **`DateTimeKind`とは**
  C#の`DateTime`型が内部的に持つ「この時刻はUTCなのか、ローカルタイムゾーンなのか、不明なのか」を表す属性（`Utc`/`Local`/`Unspecified`の3種類）。同じ日時の値でも、この属性次第で他のAPIでの扱われ方が変わる。
- **`GetDateTime`とは**
  SQLiteから読み取った列の値を、C#の`DateTime`型（`DateTimeOffset`ではなく）として取得するADO.NET APIメソッド。

【説明】

以前は、オフセット付きのタイムスタンプ（例:`2014-04-15 10:47:16+09:00`）を`GetDateTime`で読み取ると、オフセットの計算自体は正しく行うものの、返す`DateTime`値の`Kind`を`DateTimeKind.Local`（実行しているコンピュータのローカルタイムゾーン）にしていた。これは、実行環境のタイムゾーン設定によって、同じデータでも扱われ方が変わってしまう（例えば実行サーバーを日本からアメリカに移しただけで挙動が変わる）という問題を抱えていた。

`Microsoft.Data.Sqlite` 10以降は、UTCに変換したうえで`DateTimeKind.Utc`として返すようになり、実行環境に依存しない一貫した挙動になった。

【放置したときの影響】

公式の影響度は「高」。読み取った`DateTime`の`Kind`が`Local`から`Utc`に変わることで、その後の日時計算やタイムゾーン変換処理（`ToLocalTime()`等）の結果が変わりうる。

【プロジェクトでの調べ方】

このプロジェクトでは無関係。`Microsoft.Data.Sqlite`パッケージ自体を参照しておらず、PostgreSQL（Npgsql）経由の日時の読み書きにはこの変更は適用されない。
