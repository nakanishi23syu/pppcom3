# PowerShell 5.1 セキュリティパッチ(KB5074596)の検証手順

## 元の依頼内容

2025年12月9日以降のWindows Updateで、PowerShell 5.1の`Invoke-WebRequest`に
セキュリティ確認プロンプトが追加された。会社でこのパッチが「ある状態」と「ない状態」の
挙動確認作業を行っているが、このパッチだけをピンポイントで導入・削除するのが難しい。
バーチャルマシンで自由に試してよいので、手順を作って実際にテストしてほしい、という依頼。

参考にした情報源:

- <https://www.say-tech.co.jp/contents/blog/yamanxworld/2025news051>
- <https://support.microsoft.com/ja-JP/servicing/os/windows/2025/12/powershell-5-1-invoke-webrequest-preventing-script-execution-from-web-content>

## 1. パッチの内容(調査結果)

| 項目 | 内容 |
| --- | --- |
| 対策番号 | KB5074596(Microsoft公式サポートページのKB) |
| 対応するCVE | CVE-2025-54100 |
| 適用開始 | 2025年12月9日以降のWindows Update |
| 対象OS | Windows 10/11各エディション、Windows Server 2008 R2〜2025 |
| 変更内容 | `Invoke-WebRequest`を`-UseBasicParsing`・`-OutFile`のどちらも付けずに実行すると、確認プロンプトが表示されるようになる |

**実際に表示されるプロンプト(公式ドキュメント記載の文言):**

```text
Security Warning: Script Execution Risk.
Invoke-WebRequest parses the content of the web page. Script code in the web page might be run when the page is parsed.
[Y] Yes  [A] Yes to All  [N] No  [L] No to All
```

**注意点(実務上重要):** タスクスケジューラ等、無人実行(非対話セッション)で`powershell.exe`から
`Invoke-WebRequest`を`-UseBasicParsing`無しで呼んでいるスクリプトがあると、このプロンプトが
表示されたまま誰も応答できず、**スクリプトがハングする**(実際にこのVMでの検証中にも
同じ現象を再現させてしまった。3章参照)。

## 2. なぜ「ピンポイントでの導入・削除」が難しいのか(調査結果)

**結論: KB5074596という番号は、単体でインストール/アンインストールできるパッケージでは
ない。** [Microsoft Update Catalog](https://www.catalog.update.microsoft.com/)で
「KB5074596」を検索しても**該当パッケージが1件も見つからない**(実際に検索して確認済み)。

これは、この番号がMicrosoftの「Windows Release Health / Servicing」という、**毎月の
累積更新(Cumulative Update)に含まれる個々の変更点を説明するための記事番号**の体系
(URLが`support.microsoft.com/.../servicing/os/windows/2025/12/...`という形式になっている
ことからも分かる)であり、実際にこの変更が入っているのは「2025年12月の月例累積更新
（その月ごとに別のKB番号を持つ、OSごとの大きなパッケージ）」の中身の一部だから。

つまり:

- この変更**だけ**を狙って追加することはできない(累積更新をまるごと当てるしかない)。
- この変更**だけ**を狙って外すこともできない。累積更新は「その月に対応するすべての修正を
  含んだ1つの塊」として配布されるため、`wusa /uninstall`等で個別の修正だけを取り除くことは
  基本的にできない。
- さらに、**Windowsが標準でロールバックをサポートしているのは基本的に「直近1回分の
  累積更新」だけ**で、数ヶ月前の状態まで遡ってアンインストールすることは通常できない
  （古い累積更新はコンポーネントストアのクリーンアップで「置き換え確定」されてしまうため）。

会社で「ピンポイントに入れたり消したりするのが難しい」と感じたのは、まさにこの仕組みが
原因で、やり方が悪いのではなく**Windows Updateの設計上、個別のセキュリティ修正だけを
後から選んで着脱することはそもそもできない**、というのが調査の結論。

## 3. 実際にこのVMで試したこと

### 3-1. 「パッチ適用前」の状態を探す(スナップショットの調査)

このVM(`dicom-pacs-vm`)には`init`・`posgre chrome`という2つの既存スナップショットが
あったため、「パッチ適用前の状態がVM内に残っていないか」を確認した。

1. 現在の作業状態を`before-security-patch-testing-2026-08-14`として新規スナップショット保存
   （何を試しても元に戻せるようにするため）。
2. `init`スナップショットに切り替えて確認したところ、**`init`の時点で既に2026年1月14日付の
   更新(`KB5072725`・`KB5073379`・`KB5066131`)が適用済み**であることが判明。これは
   2025年12月のパッチより後なので、`init`は「適用前」の状態としては使えない
   （累積更新の性質上、2026年1月の更新には2025年12月の修正も必ず含まれているため）。
3. 現在の作業状態(2026年8月7日付の更新まで適用済み)も当然「適用後」。

**結論: このVM内に残っている過去のスナップショットは、どちらも既にパッチ適用後だった。**
真の「適用前」状態を用意するには、Windows Updateを一度も当てていない新規VMを別途
作るか、2025年12月より前の時点のスナップショット/バックアップが別途必要（今回は
用意されていなかったため、番外編として4章に「今後のための備え」を書いておく）。

### 3-2. 「パッチ適用後」の実際の挙動を確認

作業状態を`before-security-patch-testing-2026-08-14`に戻し（＝2026年8月7日更新まで
適用済みの状態）、`Invoke-WebRequest`を`-UseBasicParsing`無しで実行してみた。

**わかったこと: プロンプトを試す前に、まず別の問題（Internet Explorerエンジン未初期化）に
ぶつかった。** Windows Server環境でInternet Explorerを一度も起動したことがない状態だと、
`Invoke-WebRequest`は（このセキュリティパッチとは無関係に）
`System.NullReferenceException`で失敗することがある、という**昔からある別のPowerShell 5.1の
既知の問題**（IEのCOMコンポーネントが未初期化なため）。この2つの問題が紛らわしく重なるため、
検証の際は原因を混同しないよう注意が必要。

**さらにわかったこと: 対話セッションを介さずに(VMware Toolsのゲスト操作経由で)
`Invoke-WebRequest`を実行すると、プロンプトが表示されたままスクリプトがハングする**
（実際に本検証中に発生させ、`vmrun killProcessInGuest`でプロセスを強制終了して解消した）。
これは冒頭で触れた「タスクスケジューラでハングする」という実務上の注意点を、期せずして
このVM上でも再現できたことになる。

### 3-3. 4章の判定方法を実際に実行した結果(検証済み)

SSH経由(対話セッションではない実行)で4章のジョブ+タイムアウト方式を実際に走らせたところ、
以下の結果が得られた。

```text
=== Test 1: Invoke-WebRequest WITHOUT -UseBasicParsing ===
Wait-Job : Wait-Job コマンドレットの動作を完了できません。1 つ以上のジョブが
対話型のジョブの応答待ちでブロックされています。Receive-Job コマンドレットを
使用して対話型のジョブの出力を処理してから実行してください。
    + CategoryInfo          : Deadlock detected
    + FullyQualifiedErrorId : BlockedJobsDeadlockWithWaitJob,...
RESULT: still running after 15s -- consistent with a blocking security prompt

=== Test 2: Invoke-WebRequest WITH -UseBasicParsing ===
RESULT: SUCCESS, StatusCode=200
```

**これは決定的な証拠になった。** PowerShell自身が`Wait-Job`の時点で
「デッドロックを検出しました。ジョブが対話的な応答待ちでブロックされています」と
明示的にエラーを返している。これはまさに「バックグラウンドジョブの中で、誰も応答できない
確認プロンプトが表示されたまま止まっている」状態そのものであり、`-UseBasicParsing`を
付けた方(Test 2)は`StatusCode=200`で即座に正常終了している。**KB番号を一切参照せずに、
「このマシンではこのパッチの挙動が有効になっている」ことを実際の動作で確認できた。**

検証後、VM上に応答待ちのジョブ・プロセスが残っていないこと(`Get-Job`・`Get-Process
powershell`)も確認済み。

## 4. 推奨する検証方法(結論、動作確認済み)

「このパッチが効いているかどうか」を確実に、かつKB番号を追いかけずに判定するには、
**番号ではなく挙動そのものをテストする**のが一番確実（月ごとに累積更新のKB番号が変わっても、
この判定方法は変わらないため）。以下は3-3で実際に動作確認済みのスクリプト。

```powershell
# SSH経由・タスクスケジューラ経由等、対話プロンプトに誰も応答できない実行環境でも
# ハングせず結果を返せるよう、タイムアウト付きジョブとして実行し、
# プロンプトの有無を間接的に判定する(3-3で実際にこの通りの結果になることを確認済み)。
$job = Start-Job -ScriptBlock {
    Invoke-WebRequest -Uri "https://www.microsoft.com" -TimeoutSec 20
}
$completed = Wait-Job $job -Timeout 15
if ($completed) {
    Write-Output "パッチ未適用、またはこのページではプロンプトが出ない挙動: 正常終了しました"
    Receive-Job $job
} else {
    Write-Output "パッチ適用後の挙動の可能性: 15秒たっても終わらない(プロンプト待ちでハングしている可能性が高い)"
    Stop-Job $job
}
Remove-Job $job -Force
```

**今後、本当に「導入前/導入後」を並べて比較したい場合の進め方(未実施、方針のみ):**

1. 今のVMに次回Windows Updateをかける**直前**に、必ずスナップショットを取っておく
   （例: `before-YYYY-MM-update`）。今回はこれが無かったために3-1で行き詰まった。
2. 更新後にも`after-YYYY-MM-update`としてスナップショットを取っておけば、次回以降は
   この2つを切り替えるだけで「導入前/導入後」をいつでも比較できるようになる。
3. どうしても「2025年12月より前」の状態が必要な場合は、Windows Server 2025の評価版ISOから
   新規にVMを作り、**Windows Updateを実行する前**の状態でスナップショットを取っておく、
   という方法が最も確実（今回は時間の都合で未実施）。

## 5. まとめ

- KB5074596は「2025年12月の月例累積更新に含まれる、Invoke-WebRequestのセキュリティ強化」
  であり、**単体のパッケージとしては存在しない**(Microsoft Update Catalogで検索して0件を確認済み)。
  ピンポイントでの導入・削除が難しいのは環境やスキルの問題ではなく、Windows Updateの
  設計上そもそも不可能、というのが調査の結論。
- 挙動の実体は「`-UseBasicParsing`/`-OutFile`無しで`Invoke-WebRequest`を呼ぶと、対話プロンプトが
  出て応答が無いとハングする」。このVM(2026年8月更新まで適用済み=パッチ適用後の状態)で
  実際に再現し、`Wait-Job`が「デッドロック検出(対話的な応答待ちでブロック)」を明示的に
  報告することを確認した(3-3章)。`-UseBasicParsing`を付けた場合は`StatusCode=200`で
  正常終了することも確認済み。
- 4章のジョブ+タイムアウト方式は、KB番号を一切参照せずにこの挙動の有無を判定できる方法として
  実機で動作確認済み。今後、月例更新のKB番号が変わっても同じ判定方法がそのまま使える。
- このVMに残っていた既存スナップショット(`init`・`posgre chrome`)は両方とも既にパッチ適用後
  (2026年1月更新以降)だったため、**真の「適用前」状態との比較は今回できなかった**。
  次に控えているWindows Update適用前に必ずスナップショットを取っておけば、今後は
  前後比較ができるようになる(4章の「今後の進め方」参照)。会社の環境でも、更新を当てる前に
  スナップショット(または同等のバックアップ)を取る運用にしておくことを推奨する。
