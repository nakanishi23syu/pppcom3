## 0. そもそもDICOMって何？

DICOM（ダイコム、Digital Imaging and Communications in Medicine）は、**病院のCTやMRIなどの機器が
撮影した画像や、その付帯情報（患者名・撮影日など）を、どんな機器・どんなメーカーのソフトでも
やり取りできるようにするための「共通ルール（規格）」**です。

たとえるなら、DICOMは「医療画像業界の共通言語」のようなものです。A社のCT装置とB社の閲覧ソフトが
何の打ち合わせもなく画像をやり取りできるのは、両方とも同じDICOMという「言語」を話しているからです。

このプロジェクト(dicom-tool-3)は、このDICOMという言語を使って画像を受け取ったり(SCP)、
自分から送ってみたり(SCU)する部分を、学習用に実際に作って動かしています
(`services/DicomTool.DicomScp`)。

---

## 1. DICOMファイル1個 = 病院のカルテ1ページ（封筒に入った1組の情報）

DICOMファイルは、拡張子こそ`.dcm`という1つのファイルですが、中身は大きく2つの情報がセットで
入っています。

- **タグ情報**：患者名、患者ID、検査日、どの装置で撮ったか、体のどの部位か、といった
  「宛名や中身の説明書き」に相当する部分。
- **画素データ（ピクセルデータ）**：実際のレントゲン写真・CT画像そのもの。

これは病院のカルテを1枚の封筒に入れて送るようなものだと考えると分かりやすいです。封筒の表には
「患者の名前・生年月日・診療科」などの宛名情報（＝タグ情報）が書いてあり、封筒の中身には
実際のカルテの記載内容や画像（＝画素データ）が入っています。封筒を開けなくても表書きだけで
「誰の何の情報か」が分かるようになっている、というのがDICOMファイルの構造のイメージです。

このプロジェクトでは、`services/DicomTool.Worker/Activities/SaveToStorageActivity.cs`が
まさに「封筒の表書き（タグ）を読んで、中身を正しい棚（ストレージのフォルダ）に仕分ける」役割を
担っています。

---

## 2. Study / Series / SOP Instance UID = 図書館の「本」「巻」「ページ」という3階層の背番号

DICOMのデータは、次の3階層のIDで整理されています。図書館の本を例にすると分かりやすいです。

| DICOMの階層 | 図書館でいうと | 具体例 |
|---|---|---|
| **Study**（検査）<br>`StudyInstanceUid` | 「本のタイトル」 | ある患者が「2026年8月8日に受けたCT検査」という1つの検査 |
| **Series**（シリーズ）<br>`SeriesInstanceUid` | 「その本の第◯巻」 | 同じ検査の中の「造影剤ありの撮影」と「造影剤なしの撮影」は別の巻(Series) |
| **SOP Instance**（画像1枚）<br>`SopInstanceUid` | 「その巻の第◯ページ」 | CTは1回の撮影で何十枚〜何百枚ものスライス画像が撮れるが、その1枚1枚がSOP Instance |

つまり「1つの検査(Study)」の中に「複数のシリーズ(Series)」があり、「1つのシリーズ」の中に
「複数の画像(SOP Instance)」がある、という**入れ子構造**になっています。

それぞれの階層にUID（Unique Identifier、全世界で重複しない背番号）が振られているため、
「どの本の、どの巻の、何ページ目か」を世界中のどのシステムでも一意に特定できます。

このプロジェクトでは`shared/DicomTool.Shared/Entities/UserStudy.cs`・`UserSeries.cs`・`UserSop.cs`
がまさにこの3階層をそのままデータベースのテーブルとして表現しています（Study 1件に対して
Seriesが複数ぶら下がり、Series 1件に対してSopが複数ぶら下がる、という親子関係）。

## 3. SCU / SCP = 「手紙を送る人」と「手紙を受け取る人」

DICOM通信の世界では「クライアント/サーバー」という言葉の代わりに、次の2つの言葉を使います。

- **SCU（Service Class User）**：あるサービスを**利用する側**。多くの場合、自分から接続を
  仕掛ける側＝「手紙を送る人」。
- **SCP（Service Class Provider）**：あるサービスを**提供する側**。多くの場合、待ち構えている側＝
  「手紙を受け取る郵便受け（の持ち主）」。

ポイントは、「送る/受け取る」の役割は**やり取りする内容（サービスの種類）ごとに決まる**という点です。
CTの画像を送るモダリティ（撮影機器）は「画像送信（C-STORE）というサービスにおいてはSCU」ですが、
別のサービス（例えば検索）では逆に受け手側になることもあります。

このプロジェクトの`DicomTool.DicomScp`は、外部から送られてくる画像をいつも待ち受けている
「C-STORE SCP（郵便受けの持ち主）」であると同時に、自分自身が正しく動いているか確認するために
一時的に自分から手紙を送ってみる「C-ECHO/C-STORE SCU（送り主）」の顔も持っています
(`services/DicomTool.DicomScp/Services/DicomScuTestService.cs`)。

---

## 4. C-STORE = 手紙を「送りつける」（一方的にプッシュで送る）

C-STOREは、DICOMの画像データ一式を**送りつける**ためのサービスです。「これ送りますね」と
一方的に相手のポストに投函するイメージで、送った側は相手の応答（受け取れたかどうか）だけを
待ちます。

CTやMRIなどの実際の医療機器（モダリティ）は、撮影が終わるとこのC-STOREを使って、
待ち構えているPACS（画像保管システム）へ画像を自動的に送りつけます。

このプロジェクトでは、`services/DicomTool.DicomScp/Services/DicomScpService.cs`の
`OnCStoreRequestAsync`メソッドが、この「送りつけられた手紙」を受け取る処理そのものです。
届いた画像ファイルをいったん一時置き場（ステージング領域）に保存し、その後の重い処理
（正式な棚への仕分け・データベース登録）はTemporalという別の仕組み（
[`docs/temporal-workflow-guide.md`](./temporal-workflow-guide.md)参照）に任せます。

管理用の画面からも試せます。`services/DicomTool.DicomScp/Program.cs`が公開している
`POST /test/c-store` エンドポイントを叩くと、このプロジェクト自身が自分自身にC-STOREで
サンプル画像を送りつける、という自己疎通テストが実行できます。

---

## 5. C-FIND = 「〇〇という条件の手紙、そちらにありますか？」と問い合わせる（検索）

C-FINDは、条件を指定して「そちらにこういう患者・こういう検査の画像はありますか？」と
**問い合わせて検索する**サービスです。手紙そのものはやり取りせず、「ありますか？」
「はい、これとこれがあります（一覧だけ）」というやり取りだけが行われます。

たとえば「〇〇さんという名前で、2026年8月に撮影された検査」を条件に問い合わせると、
該当するStudy（検査）の一覧（タグ情報だけ）が返ってきます。画像の実体（画素データ）は
まだこの時点ではやり取りされません。

> **このプロジェクトでの実装状況**：C-FINDは現時点では**未実装**です
> (`docs/dicom-protocol-guide.md`にもその旨明記されています)。このプロジェクトでは
> 代わりに、Webの検査一覧画面（Worklist、`frontend/worklist`）がGraphQL経由でPostgreSQLに
> 問い合わせることで「検査の一覧を検索する」という同等の役割を実現しています。DICOM本来の
> C-FINDと同じ「検索」という目的を、DIMSEではなくWeb API（GraphQL）で代替している形です。

---

## 6. C-MOVE = 「その手紙を、私にではなく別の人に転送してください」と頼む

C-MOVEは、C-FINDで見つけた画像を「自分に直接送ってほしい」のではなく、**「別の宛先（第三者）に
転送してほしい」**と頼むサービスです。少し変わった仕組みに見えますが、実務のPACS運用では
よくあるパターンです。

たとえるなら、「あなたが持っているその手紙、私宛てではなく、向こうにいる別の担当者宛てに
転送してください」と頼むイメージです。頼まれた側（PACS）は、頼んだ相手とは別の宛先に対して
（今度は自分がSCUになって）C-STOREで画像を送りつけます。

> **このプロジェクトでの実装状況**：C-MOVEも現時点では**未実装**です。将来的な拡張候補として
> `docs/dicom-protocol-guide.md`や提案書に触れられています。

## 7. SOP Class = 「やり取りする書類の種類」

SOP Class（Service-Object Pair Class）は、「このサービスで、どんな種類の情報をやり取りするか」を
表す規格上の分類です。DICOMでは、たとえば次のように「サービス＋情報の種類」の組み合わせごとに
別のSOP Classとして区別されます。

- **Verification SOP Class**：C-ECHO専用。実データは一切含まない、いわば「確認だけの葉書」。
  中身は空っぽで、「届きましたか？」を確認するためだけに存在します。
- **CT Image Storage、Secondary Capture Image Storageなど**：C-STOREで実際の画像データを
  送るための「本物の中身が入った小包」に相当する書類フォーマット。

同じ「郵便」でも「葉書」と「小包」で扱いが違うように、DICOMでも「何を運ぶか」によって
別のSOP Classとして明確に区別され、通信の最初（アソシエーション確立時）にどのSOP Classを
使うかをお互いに宣言し合います。

このプロジェクトでは、SOPInstanceUID/SOPClassUIDという言葉が
`DicomScpService.OnCStoreRequestAsync`の中で実際にログ出力されており、「今受け取った小包は
どの種類の書類なのか」をログで確認できます。

## 8. Transfer Syntax（転送構文）= 「どの言語・どの圧縮形式で手紙を書くか」の取り決め

Transfer Syntax（転送構文）は、「同じ内容の画像データを、コンピュータの中でどうバイト列
（0と1の羅列）として表現するか」という符号化のルールです。

たとえるなら、同じ日本語の手紙でも「楷書で丁寧に平文で書く」か「速記のような専用の圧縮記法で
書く」かで、紙面の見た目（バイト列の中身）は全く変わりますが、**伝えたい内容自体は同じ**、
というイメージです。DICOMでは主に次のような転送構文があります。

- **Implicit VR Little Endian**：値の型（VR）を明示せず、規格書のお約束に従って暗黙的に
  解釈する、いわば「最低限どの機器でも読める共通の書き方」。
- **Explicit VR Little Endian**：値の型を1つ1つ明示的に書く、曖昧さの少ない現代的な書き方。
- **（JPEG等の圧縮系）**：手紙を速記や圧縮フォーマットで書くようなもの。データ量は減るが
  展開（復号）に手間がかかる。

送信側と受信側は、通信を始める最初の段階で「お互いが読み書きできる転送構文はどれとどれか」を
すり合わせ（ネゴシエーション）、一致したものだけを使います。このプロジェクトの
`DicomScpService`は学習用にシンプルさを優先し、非圧縮の転送構文（Implicit VR Little Endian /
Explicit VR Little Endian / Explicit VR Big Endian）のみに対応しています
（`AcceptedTransferSyntaxes`という配列がコード上で定義されています）。

## 9. AEタイトル（Application Entity Title）= 通信相手同士が名乗り合う「コールサイン」

AEタイトル（Application Entity Title）は、DICOM機器やシステムが自分自身に付ける、
最大16文字までの「名前」です。アマチュア無線の**コールサイン（呼び出し符号）**のようなものだと
考えると分かりやすいです。

DICOMでは、通信を始める前にお互いが「私はこういう名前(AEタイトル)です」「あなたを
こういう名前(AEタイトル)だと思って呼びかけています」と名乗り合い、**IPアドレスやポート番号が
合っているだけでなく、この名前(コールサイン)も正しく一致しないと通信が成立しません**。

無線で例えるなら、正しい周波数（IPアドレス・ポート）に合わせていても、呼びかけた相手の
コールサインが間違っていれば「その呼び出し符号には心当たりがありません」と応答を拒否される、
というイメージです。

このプロジェクトでは、`DicomScpService.OnReceiveAssociationRequestAsync`の中で、あえてこの
「コールサインの不一致チェック」を実装しており、間違ったAEタイトル宛てに接続しようとすると
明示的に拒否されるという、実務のPACSで非常によくあるトラブル（「相手先AEタイトルのスペルミスで
繋がらない」）を体験できるようになっています。

| 項目 | 値 |
|---|---|
| このプロジェクトのSCP（受信側）のAEタイトル | `DICOMTOOL3` |
| 自己疎通テスト用SCU（送信側）のAEタイトル | `DICOMTOOL3SCU` |

## 10. アソシエーション = 「電話をかけて、話して、切る」という一連の通話

DICOM通信は、HTTPのように「1回リクエストしたら1回レスポンスが返って終わり」ではなく、
**電話の通話に近い仕組み**を持っています。

1. まずTCP接続という「回線」をつなぐ。
2. 続けて「アソシエーション」という論理的な通話状態を確立する（ここでAEタイトルの名乗り合い、
   SOP Classや転送構文のすり合わせが行われる）。
3. 通話（アソシエーション）が確立している間に、複数のやり取り（C-ECHOやC-STOREなど）を
   まとめて行える。
4. 話が済んだら「では失礼します」と正式に電話を切る（アソシエーション解放）。

このプロジェクトでは実際に`services/DicomTool.DicomScp/Services/DicomScpService.cs`の中で、
「通話の始まり」（`OnReceiveAssociationRequestAsync`）、「通話の終わり」
（`OnReceiveAssociationReleaseRequestAsync`）、「通話が突然切れた場合」（`OnReceiveAbort`）が
それぞれ別のメソッドとして実装されています。

## 11. まとめ表：たとえ話 対応表

| DICOMの用語 | たとえ話 |
|---|---|
| DICOMファイル | 患者情報(タグ)＋画像データが1つの封筒に入ったカルテ1ページ |
| Study / Series / SOP Instance | 図書館の「本のタイトル」「第◯巻」「第◯ページ」の3階層 |
| SCU / SCP | 手紙を送る人 / 手紙を受け取る郵便受けの持ち主 |
| C-STORE | 手紙を一方的に送りつける（プッシュ） |
| C-FIND | 「こういう手紙、そちらにありますか？」と問い合わせる |
| C-MOVE | 「その手紙を、私ではなく別の人に転送してください」と頼む |
| SOP Class | やり取りする書類の種類（葉書 vs 小包） |
| Transfer Syntax | どの言語・どの圧縮形式で書くかの取り決め |
| AEタイトル | 通信相手同士が名乗り合うコールサイン(呼び出し符号) |
| アソシエーション | 電話をかけて話して切る、一連の通話 |
