# 手動セットアップ手順書

このドキュメントは、コードでは自動化できない「人間が手を動かす必要がある作業」をまとめたものです。
日々の起動コマンドは [`README.md`](./README.md) のクイックスタートを参照してください。ここでは
**初回だけ必要な準備**と、**実務VMへ接続を切り替える場合の手順**、**トラブルシューティング**を扱います。

---

## 1. 事前に必要なソフトウェア（初回のみ）

| ソフト | 用途 | 確認コマンド |
|---|---|---|
| .NET SDK 10.0系 | 全C#サービスのビルド・実行 | `dotnet --version` |
| Node.js 20系以上（動作確認時は24系） | Worklist/Viewer(Nuxt)の実行 | `node --version` |
| Docker Desktop | PostgreSQL・Temporal Serverのローカル起動 | `docker --version` |
| （任意）`dotnet-ef` グローバルツール | EF Coreマイグレーションを新規作成する場合のみ | `dotnet tool install -g dotnet-ef` |

Windows環境で `docker compose up -d` がエラーになる場合、**Docker Desktopアプリ自体が起動していない**
ことがほとんどです。タスクトレイにクジラのアイコンが出て「Docker Desktop is running」になるまで
（初回は30秒〜1分程度）待ってから再実行してください。

---

## 2. 初回セットアップの流れ

```bash
# 1. インフラ起動（PostgreSQL + Temporal Server + Temporal Web UI）
docker compose up -d

# 2. 起動確認（3つとも Up / healthy になっていること）
docker compose ps

# 3. Backend APIを起動 → 初回起動時に自動でPostgreSQLへマイグレーション適用 + サンプルデータ投入
cd backend/DicomTool.Api
dotnet run
# → ログに "Applying migration '...InitialCreate'" 等が出れば成功。Ctrl+Cで一旦停止してよい。
cd ../..

# 4. 以降は README.md のクイックスタート通り、各サービスを別ターミナルで起動
```

初回、Nuxtアプリ(`frontend/worklist`, `frontend/viewer`)は `npm install` が必要です
（`dicom.ts` パッケージが `postinstall` で `patch-package` を要求するため、`npm install` を
省略せず必ず実行してください）。

## 4. 常駐トレイアプリの実行について

`services/DicomTool.TrayApp` はWinForms製のため **Windows上で、かつデスクトップにサインインした
セッション**でしか正しく動作しません（タスクトレイアイコンを出すため）。リモートデスクトップの
非表示セッションやCI環境では `dotnet run` してもアイコンが表示されないことがあります。
その場合はビルド確認（`dotnet build`）のみで動作確認とし、実際の起動はローカルのWindows環境で
行ってください。

Worklist(`:3100`)からタイムラインを開く操作は、この常駐アプリが起動していないと失敗します
（Worklist側は接続失敗時に「常駐アプリが起動していません」という趣旨のメッセージを表示します）。

## 5. 外部DICOMツールでの疎通確認（任意・発展）

提案書(4-7章)にある通り、自作のSCU/SCP実装が規格に沿っているかを検証するには、既存の無料OSS PACS
ツールを「相手役」にするのが確実です。

- **dcm4che** (Java, Apache 2.0): `dcm4che-tool-storescu` 等のCLIから
  `storescu -c DICOMTOOL3@localhost:11112 <dcmファイル>` のようにこのリポジトリのSCP(`:11112`)へ
  C-STOREを送れます。
- **DCMTK** (C++, BSD類似): `echoscu`, `storescu` コマンドで同様の疎通確認ができます。
  例: `echoscu -aec DICOMTOOL3 localhost 11112`

いずれもインストールと基本操作は各ツールの公式ドキュメントを参照してください（本リポジトリのコードの
範囲外です）。AEタイトルは `DICOMTOOL3`（`shared/DicomTool.Shared/Constants/DicomNetworkConstants.cs`）
を宛先に指定してください。

## 6. 実際のVM(`192.168.93.128`)のPostgreSQLへ接続を切り替える場合

このリポジトリは既定で `docker-compose.yml` が起動するローカルPostgreSQLに接続します（学習用に
自己完結させる方針。詳細は [`docs/CONTRACT.md`](./docs/CONTRACT.md) 7章）。実務環境再現の一環で
実際のVM上のPostgreSQLに繋ぎたくなった場合は、以下のいずれかの方法で接続文字列を上書きしてください
（コードの変更は不要です）。

**方法A: 環境変数で上書き（推奨・appsettings.jsonを汚さない）**

```bash
# Windows PowerShellの例（backend/DicomTool.Api、services/DicomTool.Workerそれぞれで設定）
$env:ConnectionStrings__Dicom = "Host=192.168.93.128;Port=5432;Database=<VM側のDB名>;Username=<ユーザー名>;Password=<パスワード>"
dotnet run
```

**方法B: `appsettings.Development.json` を直接書き換える**

`ConnectionStrings:Dicom` の値を上記のVM向け接続文字列に変更してください。

> **注意**: VM側のPostgreSQLにこのリポジトリのマイグレーション（`shared/DicomTool.Shared/Migrations`）が
> 未適用の場合、Backend API起動時の `db.Database.Migrate()` が自動的にテーブルを作成しようとします。
> VM側のPostgreSQLに他の用途のデータが同居している場合は、**先にDB名を分けるか、事前にバックアップを
> 取ってから**実行してください。

このPCから `192.168.93.128` への疎通（同一ネットワーク/VPN等）が前提です。疎通できない場合は
VM側のネットワーク設定（VMwareのネットワークアダプタ設定、Windows Firewallの受信規則で5432番ポートが
許可されているか）を確認してください。

## 8. トラブルシューティング

**`docker compose up -d` が `dockerDesktopLinuxEngine` のパイプエラーで失敗する**
→ Docker Desktopアプリが起動していません。起動して1分ほど待ってから再実行してください。

**`dicomtool-temporal` コンテナが `Restarting` を繰り返す**
→ `DYNAMIC_CONFIG_FILE_PATH` に存在しないパスを指定すると起きます（本リポジトリの
`docker-compose.yml` は既にこの問題を回避済みの設定になっています。もし手元で編集して再発した場合は
該当の環境変数指定を削除し、イメージの既定値に任せてください）。

**`dotnet build` で `MSB3277`(パッケージバージョン競合)の警告が出る**
→ 実害のない警告です（0エラーであれば問題ありません）。`Npgsql.EntityFrameworkCore.PostgreSQL`と
`Microsoft.EntityFrameworkCore.Design`のバージョン差に起因する、.NETのNuGet依存解決の仕様上のログです。

**Worklistから「常駐アプリが起動していません」と出る**
→ `services/DicomTool.TrayApp` を起動していないか、Windows以外の環境で動かそうとしています。4章参照。

**アップロードしたのに検査一覧にすぐ出てこない**
→ 想定通りの挙動です。アップロードはTemporalワークフロー経由の非同期処理のため、数秒のタイムラグが
あります。Temporal Web UI(http://localhost:8233)でワークフローの実行状況を確認できます。

**完全に初期状態に戻したい**
```bash
docker compose down -v   # PostgreSQL/Temporalのデータを含めて全削除
docker compose up -d
```
（`infra/data/dicom-incoming`, `infra/data/dicom-storage` 配下の実ファイルは`docker compose down -v`
では消えません。手動でフォルダの中身を空にしてください。）
